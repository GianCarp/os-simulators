# Schedsim notes

`schedsim` is a single-core CPU scheduling simulator used to explore and compare the behaviour of different CPU scheduling policies under controlled workloads. The simulator consumes workload files generated by `workload_gen.c`, which describe job arrival times and CPU run requirements. `schedsim` reports standard scheduling metrics for the selected policies.

Currently supported scheduling policies are FCFS, SJF, and Round robin. More advanced policies such as MLFQ and ticket-based scheduling (stride and lottery) are planned. A multi-core CPU simulation mode is also planned, although simultaneous multithreading (SMT) is unlikely to be considered.

The simulator treats the input workload as immutable. Each scheduling policy operates on a private copy of the job set, allowing multiple policies to be run safely on the same workload. FCFS and SJF are implemented as non-preemptive schedulers, while Round robin is preemptive and uses a FIFO ready queue implemented as a circular buffer. When no jobs are ready to run, the simulator advances time to the next arrival.

## workload format

Workloads are provided as plain text files with the following format:

```bash
<id> <arrival_time> <run_time>
```

Each line represents a single job, where:

- `id` is a unique job identifier (starting at 1) used for deterministic tie-breaking
- `arrival_time` is the time at which the job becomes ready to run
- `run_time` is the total CPU time required by the job

## Build and run 

`schedsim` is built as part of the top level project using the root Makefile:

```bash
make schedsim
```

This produces the binary:

```bash
build/schedsim
```

The simulator can be invoked in three ways:

**1. Single policy:**

```bash
./build/schedsim <workload_file> <policy> [--time-slice N]
```

Where:

- `workload_file` is a path to a file generated by `workload_gen.c`
- `policy` is one of `FCFS`, `SJF` , or  `RR`
- If `policy` is `RR`, `--time-slice N` is mandatory, where `N` is the desired time-slice

**2. All policies**

The simulator can run all possible policies on the desired workload:

```bash
./build/schedsim <workload> --all --time-slice N
```

**3. CSV of desired policies**

Specific policies can be selected:

```bash
./build/schedsim <workload> --policies <CSV_list> [--time-slice N]
```

- Second argument must be `--policies` and it must be followed by a CSV list of policies. If the CSV list contains "RR" then the time-slice flag and value must be given


## High level architecture

To improve maintainability and enforce separation of concerns, `schedsim` is split into several header and implementation pairs:

- `schedsim.h / schedsim.c`
- `policies.h / policies.c`
- `queue.h / queue.c`

Each module has a well-defined responsibility, described below.

### schedsim.h / schedsim.c – simulator driver

This module acts as the event driver for the simulator and is responsible for:

- Parsing command-line arguments
- Loading and validating workloads
- Treating workloads as immutable input
- Dispatching private job copies to scheduling policies
- Aggregating and printing results

`schedsim_run(const workload_t *)` explicitly treats the workload as read-only input. Each policy invocation operates on a private copy of the job array, allowing multiple policies to be run safely on the same workload without shared state.

### policies.h / policies.c - scheduling logic

The `policies` module contains the implementations of the scheduling algorithms:

- FCFS
- SJF
- Round robin

This module:
- Performs no I/O
- Has no knowledge of command-line arguments or file formats
- Operates only on `job_t` state provided by the simulator

### queue.h / queue.c - ready queue abstraction

The `queue` module provides a simple FIFO queue abstraction implemented as a circular buffer. It is currently used by the Round robin scheduler to manage the ready set in O(1) time, and is designed to be reusable for more advanced schedulers such as MLFQ in the future.

## Metrics

`schedsim` prints a per policy table that reports the following metrics for each job:

- arrival - the arrival time of the job
- run - the total CPU time required by the job
- start - the time at which the job is first scheduled on the CPU
- finish - the time at which the job completes execution
- response time - the delay between a job arriving and it first being run on the CPU
- turnaround time - the total time a job spends in the system
- waiting time - the total time a job spends waiting while in the system

From these per job metrics, an aggregated policy performance is given in terms of:

- average response time 
- average turn around time
- average waiting time
- makespan - the total time required to complete the entire workload.

## Implementation notes

### job_t struct

A job is modeled via the struct `job_t`. It contains fields (`id`, `arrival_time`, `run_time`) populated by `workload_load()` in addition to fields that are populated during simulation (`start_time`, `finish_time`, `remaining_time`). 

### workload_t struct

An input workload is represented with the following struct:

```c
typedef struct {
    job_t *jobs;
    int count;
} workload_t;
```

This is a thin wrapper around a dynamically allocated `job_t` array. The number of jobs is not known at compile time, as it depends entirely on the input file, so storing jobs as a dynamically allocated array to handle unknown workload sizes is natural. 

Storing jobs in a contiguous array allows the workload to be sorted once by arrival time, then processed with a single forward index to efficiently enqueue newly arrived jobs during simulation.

`workload_load()` is responsible for allocation and initialisation.
`workload_free()` is responsible for clean up.

### schedsim_run()

`schedsim_run()` is a dispatcher, it looks to see what policy is selected and calls the appropriate policy.  

```c
void schedsim_run(const workload_t *workload, enum sched_policy policy, int time_slice);
```

Note that `workload` is passed as `const workload_t *`.  Each run makes a mutable copy of the jobs array so the original input remains unchanged, enabling multiple policies to be executed on the same workload without re-reading. 

### main() argument parsing

The argument parsing logic in `schedsim` is designed to support running multiple scheduling policies in a single invocation of the program, while enforcing clear and explicit constraints on valid combinations of flags.

Rather than relying on generic option parsing libraries, the simulator performs explicit positional checks on `argv`. This keeps control flow easy to reason about and ensures that invalid combinations of arguments are rejected early with clear error messages.

At a high level, the parser enforces the following invariants:

- A workload file must always be provided as the first argument
- Exactly one of the following modes must be selected:
    - single policy
    - all policies
    - a user-specified list of policies
    - If Round robin is selected in any mode, a valid time slice must be provided

To support this, the parser first validates that `argc` is within a fixed range, min 3 and max 6.  The parsing logic then proceeds in order of decreasing generality:

1. **All-policies mode (`--all`)**  
    This is the simplest case to handle. If `--all` is present, the simulator enables all supported policies. As Round robin is included implicitly, the presence of 
    `--time-slice N` is mandatory and validated immediately.
    
2. **Policy list mode (`--policies`)**  
    If `--policies` is specified, the following argument is treated as a comma-separated list of policy identifiers.  This string is passed unchanged as a `const char *` to `parse_policy_list()`, which tokenises the list and validates each policy name.
    
    The decision not to modify `argv` directly makes the parsing logic easier to test in isolation and keeps `parse_policy_list()` reusable as a general CSV parser rather than one tied to command-line arguments.
    
    Once the policy list is parsed, the simulator scans the resulting policy array to determine whether Round robin is present. If so, it enforces that a valid time slice is supplied.
    
3. **Single-policy mode**  
    If neither `--all` nor `--policies` is present, the simulator treats the second argument as a single policy identifier. This path has the fewest moving parts and serves as the base case for the parser.

By structuring the argument parsing this way, `schedsim` ensures that:

- Invalid combinations of flags are rejected deterministically
- The presence of Round robin always implies a valid time slice
- Policy selection logic remains decoupled from policy execution

This keeps the simulator’s control flow explicit and avoids hidden behaviour that could obscure scheduling results.

### workload_load()

Once the arguments have all been parsed, `workload_load()` is called. At a high level, this is simply completing the following steps:

1. open the file
2. call `populate_workload()`, which:
	1. Dynamically allocates heap memory for the array of `job_t`.
	2. Reads the file line by line, performing appropriate error checking
	3. If all error checks pass, for the line, append the job to the array.
	4. Repeat 2 and 3 until EOF. Increase allocated memory as required, by doubling the capacity.
3. Sort the jobs by arrival time, via the helper function `compare_jobs_by_arrival()`

### schedsim_run()

Main then simply iterates over the number of policies that have been entered into the `policies` array, calling `schedsim_run()` for each policy. 

`schedsim_run()` begins by creating a mutable copy, then calling `run_policy()` which itself calls the appropriate policy to populate the `jobs` array with the appropriate data. When `run_policy()` returns, `schedsim_run()` calls `print_results()` to provide the user with the information from the simulation.

**FCFS**

`fcfs()` implementation is simple, just iterate over the jobs sequentially (as they are already in order of arrival time), updating fields within the struct, and then increment time appropriately until all jobs are completed.

**SJF**

`sjf()` is more nuanced than `fcfs()`.  It keeps track of the number of jobs completed, and iterates over all jobs looking for the 'best' option - i.e. a job with `arrival_time <= current_time`, has the shortest run time, and then use ID to distinguish between otherwise equally worthy jobs.

If no best job is found, need to push time forwards to be at the start of the next best job.

**RR**

Round robin (RR) is a preemptive scheduling policy. Jobs that are ready to run are scheduled in FIFO order, and each job receives at most a fixed time slice. If a job does not finish within its slice, it is preempted and placed at the back of the ready queue.

To implement RR efficiently, we need a data structure that:

- Preserves FIFO order
- Supports push (enqueue) and pop (dequeue) in O(1)
- Avoids per-operation heap allocation and pointer chasing
    
A linked list can provide O(1) push/pop but involves pointer chasing and typically more allocation / worse cache locality. Scanning the entire job list each time-slice is also undesirable because it becomes O(n) work per scheduling decision.

So, a circular buffer FIFO queue was used in the implementation of RR.

**Circular buffer queue design**

The ready queue stores integers, where each integer is an index into the `jobs[]` array (not a copy of `job_t`). This keeps the queue small and avoids moving structs around.

```c
typedef struct {
	int *buf; // pointer to dynamically allocated array (circular buffer storage)
	int cap; // capacity of the buffer, typically num_jobs
	int size; // current number of elements in the queue
	int head; // index of front element
	int tail; // index of next insertion position
} queue_t;
```

The key idea is that `head` and `tail` wrap around when they reach the end of the array:

```C
idx = (idx + 1) % cap;
```

Tracking `size` explicitly avoids ambiguity where `head==tail` is either a full or empty queue. 

The queue has the following invariants:

- `cap > 0`
- `0 <= size <= cap`
- `head` points to the next element to dequeue
- `tail` points to the next free slot to enqueue

The queue has the following operations:

- `q_init(q, cap)` allocates the backing array and resets the queue to empty.
- `q_free(q)` frees the backing array and resets fields to safe values.
- `q_empty(q)` returns whether `size == 0`.
- `q_push(q, v)` writes at `tail`, advances `tail`, increments `size`.
- `q_pop(q)` reads at `head`, advances `head`, decrements `size`.

All operations are O(1).

**Round robins use of the queue data structure**

RR uses the fact that `jobs[]` is sorted by `arrival_time`. That makes it possible to enqueue newly arrived jobs with a single forward moving index, `int next_arrival`. 

This index is the next job that has not yet been placed into the ready queue. As the jobs are sorted by arrival time, can enqueue all jobs whose `arrival_time <= current_time` by advancing `next_arrival`, no scanning needed.

Each iteration of the Round robin loop models one scheduling decision and proceeds as follows:

1. **Handle idle CPU (time jump)**  
    If the ready queue is empty but there are still jobs that have not yet arrived, advance `current_time` to the arrival time of the next job (`jobs[next_arrival].arrival_time`).  
    This models the CPU being idle until work becomes available.
    
2. **Admit newly arrived jobs (first-time enqueue)**  
    Enqueue all jobs whose `arrival_time <= current_time`.  
    This uses the `next_arrival` index, which monotonically increases and ensures that **each job is admitted to the system exactly once** when it first arrives.
    
3. **Select and run the next ready job**  
    Pop the job index at the head of the ready queue.
    
    - If this is the first time the job has been scheduled, record its `start_time`.
    - Run the job for `min(time_slice, remaining_time)`.
    - Advance `current_time` by the amount run and decrement the job’s `remaining_time`.
        
4. **Admit jobs that arrived during the time slice**  
    After advancing time, enqueue any additional jobs whose arrival time falls within the executed time slice.  
    Again, `next_arrival` guarantees these are **new jobs**, not ones that have already run.
    
5. **Completion or re-queue**
    
    - If the job has completed (`remaining_time == 0`), record its `finish_time`.
    - Otherwise, **re-enqueue the same job index at the tail of the ready queue**, preserving FIFO order for Round robin rotation.


**Invariants**

- A job is only enqueued via `next_arrival` once, at its  arrival
- A job is only re-enqueued after it has been popped and run, if it has run time left
- No job can exist in the ready queue at more than one location.
- The ready queue always represents the current FIFO ordering of runnable jobs
